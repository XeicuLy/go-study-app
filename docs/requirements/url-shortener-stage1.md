# URL短縮API (Stage 1) 要件定義書

## 概要

- **解決する課題**: Goの文法基礎（Tour of Go相当）は一周したが、「何から実装すればいいのか分からない」状態から抜け出せていない。文法を知っていることと、Goらしい構造を自分で組み立てられることの間にあるギャップを、題材を絞った小さなAPIを自分の手で完成させることで埋める。
- **対象ユーザー**: 実装者本人（フロントエンドエンジニア / TypeScript・Vue・React 実務3〜4年 / Go学習者）。APIの利用者も本人であり、curl または REST クライアントから叩く。利用シーンは学習時間中のローカル環境で、本番運用・第三者への公開は想定しない。
- **参考にした類似プロダクト・事例**: 特になし（題材の元ネタとして bit.ly / TinyURL 等の一般的なURL短縮サービス）。使用ライブラリの選定は本要件定義の範囲外とし、実装着手時に別途判断する。

## ゴール

認証なしのURL短縮APIを完成させることを通じて、Goらしい設計（レイヤリングとエラーハンドリング）を体得する。具体的には、以下の2点を満たした時点で Stage 1 を完了とし、Stage 2（JWT認証）へ進む。

1. 全エンドポイントが handler / service / repository の3層に分離されており、repository が interface として定義され差し替え可能になっていること
2. 独自エラーを定義し、`errors.Is` で判定して適切なHTTPステータスに変換できていること

なお本ドキュメントは、段階的なロードマップのうち **Stage 1 のみ**を対象とする。Stage 2（JWT認証とユーザーごとの管理）および Stage 3（アクセスログのchannel経由非同期バッファリング）は、別途要件定義を行う。

## 前提知識と学習項目

本要件が要求する内容には、Tour of Go の範囲外の項目が多く含まれる。実装中に詰まった際、「理解不足」ではなく「未習の項目に当たった」と切り分けるための地図として記載する。

### すでに一周した範囲（Tour of Go 相当）

- 変数・型・関数・struct・メソッド・slice・map
- interface の定義と、暗黙的な実装（`implements` を書かない）
- `error` を戻り値として返す作法

### 本要件で新しく学ぶことになる項目

| 関連する要件 | 新しく学ぶこと |
| --- | --- |
| F1〜F4, F8, F10 | `net/http` によるサーバー実装とルーティング（Go 1.22以降の `ServeMux` のパターン構文） |
| F1, F3, F7, F8 | `encoding/json` によるデコード / エンコードと、構造体タグ |
| F2 | `http.Redirect` とリダイレクト系ステータスコードの使い分け |
| F5, NS3 | `net/url` によるURLのパースと検証 |
| F7, NM3 | センチネルエラーの定義、`fmt.Errorf` の `%w` によるラップ、`errors.Is` / `errors.As` |
| NS1 | `crypto/rand` と、バイト列から文字列（base62）への変換 |
| NS5 | `http.MaxBytesReader` によるリクエストサイズ制限 |
| NM1, NM4, NM6 | パッケージ分割と依存の向きの制御、コンストラクタ注入によるDI |
| NM5, NM7 | `testing` パッケージ、テーブル駆動テスト、`httptest` によるハンドラのテスト |
| ストレージにSQLiteを選ぶ場合 | `database/sql` とドライバ、プレースホルダによるパラメータ化 |

これらは「知らなくて当然」の項目である。特に完了条件の一方である `errors.Is` は Tour of Go に登場しないため、初見であることを前提に進めてよい。

## 機能要件

| ID | 機能 | ユーザーストーリー | 優先度 |
| --- | --- | --- | --- |
| F1 | 短縮URLの作成 | APIの利用者として、長いURLをPOSTして短縮コードを発行したい。なぜなら共有しやすい短いURLが必要だから | MUST |
| F2 | 短縮コードによるリダイレクト | APIの利用者として、短縮URLにアクセスすると元のURLへ転送されたい。なぜならそれが短縮URLの存在意義だから | MUST |
| F3 | 短縮URL一覧の取得 | APIの利用者として、登録済みの短縮URLを一覧で確認したい。なぜならどのコードが何に対応しているか把握したいから | MUST |
| F4 | 短縮URLの削除 | APIの利用者として、不要になった短縮URLを削除したい。なぜなら誤って作ったURLを無効化したいから | MUST |
| F5 | 作成時のURLバリデーション | APIの利用者として、不正なURLを送った際に400と理由を受け取りたい。なぜなら何が悪かったのか分からないと直せないから | MUST |
| F6 | 存在しない短縮コードへの404応答 | APIの利用者として、存在しないコードを指定した際に404を受け取りたい。なぜなら「無い」のか「壊れている」のか区別したいから | MUST |
| F7 | 統一されたエラーレスポンス形式 | APIの利用者として、すべてのエラーが同じJSON構造で返ってきてほしい。なぜならクライアント側のエラー処理を1か所にまとめたいから | MUST |
| F8 | 短縮URLの単体取得 | APIの利用者として、特定の短縮コードの詳細だけを取得したい。なぜなら一覧全体を取らずに1件を確認したいから | SHOULD |
| F9 | カスタムエイリアスの指定 | APIの利用者として、短縮コードを自分で指定したい。なぜなら意味のある文字列のほうが共有時に伝わりやすいから | SHOULD |
| F10 | ヘルスチェック | 学習者として、サーバーが起動しているかを1リクエストで確認したい。なぜなら3層を通さない最小の疎通確認が欲しいから | COULD |
| F11 | アクセス数の記録・表示 | APIの利用者として、各短縮URLが何回アクセスされたか知りたい。なぜならどのURLが実際に使われているか把握したいから | COULD |
| F12 | 有効期限の設定 | APIの利用者として、短縮URLに有効期限を設定したい。なぜなら一時的な共有には期限切れが必要だから | COULD |

### 仕様の詳細

| 項目 | 内容 |
| --- | --- |
| エンドポイント構成 | `POST /links` / `GET /links` / `GET /links/{code}` / `DELETE /links/{code}` / `GET /{code}`（リダイレクト） / `GET /healthz` |
| 短縮コード生成 | `crypto/rand` によるランダム7文字（base62） |
| リダイレクト | `302 Found` + `Location` ヘッダ |
| 重複した長いURL | 排除しない（毎回新しいコードを発行） |
| 削除方式 | 物理削除 |
| URLバリデーション | `net/url` でパース可能 / スキームが `http` または `https` / 2048文字以内 |
| エラーレスポンス形式 | `{"error": {"code": "NOT_FOUND", "message": "..."}}` |
| 一覧レスポンス形式 | `{"items": [...]}`（将来ページネーションを足しても形が崩れない構造） |
| 想定ステータスコード | 201（作成）/ 200（取得）/ 204（削除）/ 302（リダイレクト）/ 400 / 404 / 409（F9採用時）/ 500 |
| ストレージ | インメモリまたはSQLite（NM2により、どちらで始めても後から差し替え可能であること） |

### 推奨する実装順

「何から実装すればよいか」で詰まらないための着手順の目安。

`F10（ヘルスチェック）` → `F2（リダイレクト）` → `F1（作成）` → `F3（一覧）` → `F4（削除）` → `F5〜F7（エラー周りの整理）` → `F8` → `F9` → `F11 / F12`

F10 でサーバー起動とルーティングのみを確認し、次に F2 で「読む」経路を3層まるごと縦に1本通す。読み取りは書き込みより状態管理が単純なため、3層の輪郭を掴むのに適している。

## 非機能要件

### セキュリティ

Stage 1 には認証がないため、「認証で守る」観点ではなく「認証がなくても壊れない作りにする」観点で定義する。

| ID | 要件 | 検証方法 |
| --- | --- | --- |
| NS1 | 短縮コードは `crypto/rand` を用いて生成し、連番・タイムスタンプ・UUIDv1 など推測可能な値を使わない | 連続して作成した10件のコードに規則性がないこと |
| NS2 | SQLiteを使用する場合、SQLは必ずプレースホルダ（`?`）でパラメータ化し、文字列結合でクエリを組み立てない | repository 層に `fmt.Sprintf` によるSQL組み立てが存在しないこと |
| NS3 | リダイレクト先として登録できるURLは、スキームが `http` または `https` のもののみとする。`javascript:` `data:` `file:` 等は `400` で拒否する | `javascript:alert(1)` をPOSTすると400が返ること |
| NS4 | エラーレスポンスに内部情報（SQLのエラー文、スタックトレース、ファイルパス）を含めない。内部詳細はサーバーログにのみ出力する | DBを意図的に壊した状態でリクエストし、レスポンスが汎用的な500メッセージであること |
| NS5 | リクエストボディのサイズに上限を設ける（`http.MaxBytesReader`、上限1MB） | 1MBを超えるボディをPOSTすると413または400が返ること |

### 保守性・拡張性

本プロジェクトの実質的な主目的。すべて外部から機械的に確認できる基準とする。

| ID | 要件 | 検証方法 |
| --- | --- | --- |
| NM1 | handler / service / repository の3層に分離し、依存の向きが handler → service → repository の一方向であること | service パッケージが handler を、repository が service を import していないこと |
| NM2 | repository は interface として定義され、service は具象型ではなく interface にのみ依存すること | service のコードを1行も変えずに、インメモリ実装とSQLite実装を差し替えられること |
| NM3 | ドメイン固有のエラー（`ErrNotFound` / `ErrInvalidURL` / `ErrCodeConflict`）を独自に定義し、handler は `errors.Is` で判定してHTTPステータスへ変換すること | handler にエラーメッセージの文字列比較による分岐が存在しないこと |
| NM4 | HTTPへの変換責務は handler 層のみが持つこと | service / repository パッケージが `net/http` を import していないこと |
| NM5 | service 層のユニットテストが、HTTPサーバーもDBも起動せずに実行できること | モック（またはインメモリ実装）の repository を注入して `go test` が通ること |
| NM6 | 依存の組み立て（DI）は `main` の1箇所に集約し、DB接続・ロガーをグローバル変数で共有しないこと | パッケージレベルの可変なグローバル変数が存在しないこと |
| NM7 | MUST に分類した機能（F1〜F7）には、service 層のユニットテストと handler 層のテーブル駆動テストを用意すること | 該当パッケージに `_test.go` が存在し、正常系と異常系の両方を含むこと |
| NM8 | Stage 2（JWT認証）・Stage 3（アクセスログの非同期化）の追加が、既存3層の構造変更ではなく追加で済むこと | Stage 2 着手時に変更が必要なのは、モデル定義・repository実装・ミドルウェア追加に限定されること |

> **NM2 に関する補足**: NM2 は Stage 1 完了時点での最終状態を示す基準であり、着手時点から interface を切る必要はない。まず具象型で1本動かし、2つ目の実装が必要になった時点で interface を抽出する順序を許容する。Goの interface は実装側に宣言を書かないため、後から抽出しても既存の具象型を変更せずに済む。

### 定義しなかったカテゴリ

パフォーマンス / 可用性 / スケーラビリティ / コスト / 運用・監視 は、個人学習用でローカル完結・本番運用を想定しないため、Stage 1 では要件を定義しない。

## スコープ外

以下は Stage 1 では対象外とすることを確認済み。

- **一覧のページネーション**（`limit` / `offset`）— レスポンス形式のみ将来の追加に耐える構造にしておく
- **JWT認証・ユーザーごとの管理** → Stage 2 で別途要件定義
- **アクセスログのchannel経由非同期バッファリングとバッチ書き込み** → Stage 3 で別途要件定義
- **CORS対応・フロントエンド連携** — Stage 1 は curl / REST クライアントで完結させる。ただし将来フロントエンドから叩くことを見据え、JSONレスポンス形式とエラーレスポンス構造は Stage 1 の段階で確定させる
- 同一URLの重複排除、論理削除、カスタムドメイン、QRコード生成
- 本番デプロイ・ホスティング
